## 为每项功能回答这些问题

| 要回答的问题 | 证据设计 |
| --- | --- |
| 用户操作有没有到达业务层？ | 入口被接受／拒绝；业务关联 ID；实际获得的参数类别，避免记录敏感原值 |
| 为什么没有继续执行？ | 前置条件和固定拒绝原因，例如未配置、频道过滤、前台未知、目标失效 |
| 是在等待还是已经找不到？ | 区分开始、进度、耗尽、超时和取消；摘要包含请求量、观察量或队列深度等相关计数 |
| 任务有没有跨越边界？ | 派发与消费使用同一关联 ID；异步重试有 attempt；旧 generation 的结果明确丢弃 |
| 结果由哪一层确认？ | 区分缓存命中、外部请求返回、系统输入返回、业务验证、UI 应用／拒绝；没有外部证据时结果保持未知 |
| 开始录制时任务已经在运行怎么办？ | 记录当前状态快照、功能日志能力标识与本轮关联边界；累计计数明确从何时开始 |
| 记录本身是否不完整？ | 使用已有丢帧、截断、脱敏、写失败和回放不完整标识；不能把缺日志当作功能成功 |

原因码应描述证据，例如 `unsupported_channel`，而不是猜根因，例如“玩家关闭某设置”。“没有找到时间戳前缀”只能说明被扫描范围中未命中，不能说明游戏没有发言。

## 示例：持续扫描却收不到消息

一次扫描需有可关联的开始、受限进度和终态，并能辨认初次定位、恢复定位或后台盘点。使用本次会话内的序号即可，不需要把内存地址当 ID。

计数至少应回答实际涉及的分歧：扫描是否前进、短读是否发生、是否匹配前缀、候选结构是否有效、元数据／消息格式是否支持、频道是否被当前来源排除、是否只看到相同快照。已发现候选与读取器已接入要分别表达。统计应在每次观察后累计，不能只求和当前缓存里的读取器，否则淘汰缓存后会倒退。

后续消息交付还应能在读取、来源合并、翻译控制器之间对应；不能只证明某个解析器曾找到消息。统计重复检查次数时说明它不等于交付消息数。

## 示例：新增游戏内快捷功能

只采用真实存在的阶段：收到触发、输入上下文检查、目标解析、派发、执行回执、取消／过期及必要的最终验证。一次“系统输入调用返回成功”只能证明该调用的结果，不能写作“游戏已完成目标动作”。后台焦点、聊天框或目标状态未知时，应记录未知及决策，而不是填入上次成功值。

## 导出验收

在临时目录构造真实 `DiagnosticRecorder`，通过业务入口触发合成场景，导出 ZIP 后按已知日志文件读取 JSON。验证下列与本次改动有关的可观察行为：

- 成功路径和关键失败路径能重建顺序与关联，必需字段在写入和导出双重过滤后仍存在。
- 无输入／持续等待有受限摘要；超时、取消、旧代结果、部分成功等实际分支不会只留下开始事件。
- 关闭诊断不增加游戏／网络／输入动作，记录器抛异常或拒绝写入不改变业务结果。
- 敏感测试值经过脱敏，不支持元数据的拒绝摘要不泄漏正文，事件量与字段大小有边界。
- 旧格式日志明确缺少何种能力；回放一致只支持已记录的业务判断，实机效果另列待验证。

按功能选择必要测试，不为不存在的异步、超时或 UI 边界制造模板测试。交付时给出具体命令、结果、日志覆盖和仍需要用户复现的证据。

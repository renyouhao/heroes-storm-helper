# 分支、Tag 与发布规范

用于建立或执行分支、候选版、正式版和紧急修复流程。先核对项目现有约定、发布方式及用户授权；以下是可调整的默认方案，不自动授权创建仓库、修改保护规则、合并或发布。

## 按实际需求选择分支

默认只保留一个集成主干和短期任务分支。主干应可构建并通过必要检查，但不保证等于用户正在使用的最新正式版；已发布版本由固定 Tag 和对应产物确定。

| 用途 | 名称示例 | 从哪里开始 | 完成后 |
| --- | --- | --- | --- |
| 集成主干 | `main`，沿用已有名称 | 已有主干 | 持续维护 |
| 新功能 | `codex/feat-tab-broadcast` | 已同步的目标主干 | PR 检查并集成 |
| 常规修复 | `codex/fix-lobby-reconnect` | 已同步的目标主干 | PR 检查并集成 |
| 文档或技能 | `codex/docs-release-policy` | 对应目标分支 | 只包含本任务内容 |
| 正式版紧急修复 | `codex/hotfix-chat-reconnect` | 故障版本的正式 Tag 或已核实维护分支 | 修复发布，并把修复回灌主干 |
| 发布稳定化（按需） | `codex/release-1.1` | 本次候选的确定提交 | 仅接受阻断修复、版本及说明更新，集成时回灌修复 |
| 多版本维护（按需） | `codex/maint-1.x` | 需要持续支持的正式版本 | 明确维护范围、版本规则及停止维护条件 |

名称只是例子，前缀遵守当前仓库和运行环境。使用小写英文、数字及连字符表达一个任务；已有 Issue 编号时可加入。分支名不充当版本事实来源，也不应因规范更新而批量改名历史分支。

只有“本版稳定化期间，主干还要继续接受下一版功能”时才建立发布分支；只有确实要支持多个已发布版本时才维护多条版本线。两段版本默认不提供三段 SemVer 那样的 PATCH 维护空间，需要长期并行维护时先确定版本方案。

普通任务优先通过 PR 集成，并按仓库约定使用 squash 或 merge；不擅自改变既有合并策略。若采用 squash，最终发布提交是合并后的新提交。删除任务分支前核实内容已按该合并方式保留且无独有工作，并遵守用户的清理授权；不要根据分支名推断可以删除。

## Tag、版本和通道

| 类型 | 默认两段版本示例 | 使用三段 SemVer 的项目 | 分发方式 |
| --- | --- | --- | --- |
| 本地临时测试 | 不要求 Tag，记录提交与构建标识 | 同左 | 本地测试包，注明尚未发布 |
| 早期体验 | `v1.1-alpha.1` | `v1.1.0-alpha.1` | GitHub prerelease，手动下载或受支持的测试通道 |
| 功能测试 | `v1.1-beta.1` | `v1.1.0-beta.1` | GitHub prerelease |
| 发布候选 | `v1.1-rc.1` | `v1.1.0-rc.1` | GitHub prerelease，完成发布前验收 |
| 正式发布 | `v1.1` | `v1.1.0` | 正式 Release 和已核验程序附件 |

不必逐个经历 alpha、beta、rc；按测试需要选择。两段形式是本技能默认约定，不是标准 SemVer；项目已有规范优先，不混用 `v1.1` 和 `v1.1.0` 作为两个不同正式版本。预发布的附加名称是否可用，还取决于版本文件、构建工具、包名和更新器。

Tag 标记一个确定提交；Release 提供说明与下载附件；分支承载后续工作。创建 Tag 不会自动产生可执行文件，GitHub 的 “Source code” 下载只包含标签源码。

发行采用附注标签（`git tag -a`），已有签名条件时可用签名标签（`git tag -s`）。显式指定完整构建提交，记录版本、累计变更摘要、验证和清单位置。不要只写一个随当前 checkout 变化的 `HEAD` 而不核实提交。

已对外发布的 Tag 不移动、不复用；同一 beta/rc 交付新内容须生成下一个序号。正式版新内容使用新版本。标签撞名时比较标签对象和解引用提交；不同则停止，不用 `tag -f` 或强推覆盖。仅用户明确要求历史标签改名时，执行主技能中的迁移与附件核验流程。

### 客户端更新器是发布约束

沿实际代码检查：版本字符串如何解析和比较、查询哪个 API、是否忽略 draft/prerelease、附件筛选规则、包内版本如何核验。还需测试 RC 到正式版的比较，以及 Tag、程序版本和文件名的对应关系。

若更新器只接受数字正式版本或只查询 `releases/latest`，beta/rc 仅作为手动测试通道，不能宣称客户端可自动安装。不要将测试版标成正式版来让旧更新器看见，也不要把候选版标为 latest。测试通道、独立通道标识和候选版比较支持需要另行实现及验证。

例如，公开 Tag `v1.1` 与内部 `1.1.0` 可以按项目规范映射为同一版本；但内部都写 `1.1.0` 无法区分 rc.1、rc.2 与正式版。需要手动安装并明确说明此限制，或先完善通道和版本模型。只有在最终提交、构建元数据及文件完全相同且项目规则允许时，才可复用候选产物；任何改动都须从最终提交重新构建验证。

## 紧急修复与版本占用

紧急修复的目标是交付故障版本所需的最小修复，不能把主干尚未发布的功能顺带带给用户。

1. 核实故障版本的正式 Tag、解引用提交、当前 Release 和产物摘要，从该提交或合适维护分支开短期 hotfix 分支。
2. 实现必要修复，并在该基线验证。已有主干修复可按需 `cherry-pick -x`，但先核对依赖，避免把未发布功能带入。
3. 依据项目版本规则选择一个未占用的新正式版本，从确定的已提交状态构建验证，发布后核实远程 Tag、Release 和附件。
4. 将等价修复同步到主干及受影响的活跃发布线；可以 cherry-pick，也可以按项目流程合并。尽量将代码修复与发行版本调整分开提交，回灌时保留主干下一版的版本元数据，解决冲突后重新验证。记录关联，避免重复修复、版本倒退或后续回退。

两段版本的例子：正式版为 `v1.0`，下一功能版候选暂定 `1.1`，此时旧版需要紧急修复。兼容修复仍应使用下一个未占用的两段正式版本；若 `1.1` 尚可用，可由修复版先占用 `v1.1`，原功能候选后移为 `1.2` 并统一更新元数据、说明和包。已发布的 `v1.1-beta.1` 保持原样，在说明中标记该功能候选已被后续版本替代，不移动标签。

若版本已被正式版占用，则继续选择下一个未占用版本，不能覆盖。若用户需要长期固定 `1.0` 版本线并持续发补丁，先确定是否迁移到三段版本，不能在既定两段规则下偷偷创造 `v1.0.1`。三段 SemVer 项目才按既有规则使用如 `v1.0.1` 的兼容修复号。

## 从提交到下载包

按下列链路留下可核验记录：

`本次目标分支 → 必要检查/审查 → 确定发布提交 → 干净构建 → 实际产物核验与 SHA256 → 附注 Tag → Release 附件 → 远程复核`

- PR 合并后若提交发生变化，重新选择构建提交并构建验证；不能让 Tag 指向合并后提交却上传旧分支构建的包。确实从发布分支直接交付时，Tag 与包指向同一个已核验发布提交，并记录回灌状态。
- 存在 CI 时运行适用检查；尚无 CI 时执行本地检查并明确记录，不把“写入规范”说成已经启用 Actions 或分支保护。
- 正式发布前保留版本、完整提交 SHA、文件名与 SHA256、相对上一正式版的更新、必要测试与待验收项。密钥和本地用户状态不进入源码或产物。
- 测试 Release 标记 prerelease 并避免成为 latest；正式 Release 经授权后再发布并核对稳定更新源。Tag 或上传失败时先读取远程状态再重试，保留已有成功结果，不用同名附件覆盖掩盖错误。
- 保护主干及 `v*` 标签、检查门禁与签名属于可以按需采用的仓库设置；规范文档不代表这些设置已经开启，修改设置需要在用户授权范围内。

## 命令示例

以下为 PowerShell 模板，尖括号占位符必须替换；每一步核验成功再继续，不整段盲跑。`github` 仅是假设已经核实的目标 remote 名称；实际仓库可能不同。

```powershell
# 先核实 remote URL、基线和本次全部待推提交。
git remote -v
git fetch github main
git log --oneline github/main..<任务分支>
git diff --stat github/main...<任务分支>
git push github <任务分支>:refs/heads/<任务分支>

# 已获发布授权，且目标提交和同一份产物均已验证时。
git rev-parse '<构建提交>^{commit}'
git ls-remote --tags github refs/tags/<新Tag> 'refs/tags/<新Tag>^{}'
git tag -a <新Tag> <完整构建提交SHA> -F <标签说明文件>
git push github refs/tags/<新Tag>:refs/tags/<新Tag>
gh release create <新Tag> <已验证ZIP> <SHA256清单> --repo <owner/repo> --verify-tag --notes-file <发布说明文件>

# 远程复核：附注标签需同时核对解引用后的 commit。
git ls-remote --tags github refs/tags/<新Tag> 'refs/tags/<新Tag>^{}'
gh release view <新Tag> --repo <owner/repo> --json tagName,isDraft,isPrerelease,assets,url
```

测试 Release 的 `create` 命令追加 `--prerelease --latest=false`。主技能已有的多行文件要求同样适用。示例不授权任何真实推送或发布；仅本地提交、仅打包或仅同步技能时，到对应步骤结束。

## 参考来源与取舍

- [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)：参考短期任务分支、PR 和检查后集成，适合作为小项目默认流程。
- [Kubernetes Release Cycle](https://kubernetes.io/releases/release/)：参考发布分支稳定化、维护线的 cherry-pick 管理；不直接照搬其发布周期、人员组织与三段版本规则。
- [Git 官方 Tag 文档](https://git-scm.com/docs/git-tag)：核对附注标签、可选签名与标签对象行为。
- [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)：核对 Tag、Release 和源码归档/二进制附件的关系。
- [GitHub CLI 发布命令](https://cli.github.com/manual/gh_release_create)：核对 `--verify-tag`、`--prerelease`、`--latest=false` 和附件上传参数。

以上资料用于说明取舍；两段版本、`codex/` 示例及默认规模方案是本技能的建议，不是这些开源项目的统一要求。

# 提交代码、发行打包与版本发布

用中文说明本次实际更新、版本判断和验证结果。本地开发完成后的发行打包视为准备将要发布的内容，打包前就应用版本规则。提交、推送、发布分别按用户授权执行；“提交代码”默认仅本地 commit，“本地打包”不自动推送、打远程标签或发布 Release。已有明确授权时直接完成，遇到目标冲突再问。

涉及分支规划、Tag 命名、预发布、正式发布或旧版紧急修复时，先读 [分支、Tag 与发布规范](references/branch-tag-release.md)。该参考包含按规模选择分支、两段版本的紧急修复冲突、更新器兼容检查及发布命令示例；项目和用户已有约定优先。

## 确定范围

1. 读取适用 AGENTS.md，检查 status、已暂存与未暂存 diff、分支、远程、近期 commit、远程标签和 Release。不要假设 origin 就是 GitHub；从实际 URL 确定目标仓库。
2. 阅读相关文件与调用链，归纳用户可感知的变化。只提交本任务文件或片段；保留无关未提交/已暂存工作，不直接 git add .。检查待提交内容不含密钥、本地配置、日志、数据库和构建临时文件。
3. 发行打包和发布的版本基线取目标仓库已核实的正式发布版本；比较其提交到本次拟打包/发布内容的累计变化，不能只看最后一个 commit、改动行数或本地未发布版本号。只提交且不打发行包、不发布时可以给版本建议，但不必修改版本文件。离线时可用最近已核实的发布记录并注明依据，不把未核实的本地标签当作最新正式版。

## 选择分支与同步范围

- 小项目默认采用主干与短期任务分支；`main` 是通过检查的集成主线，当前已发布内容由正式 Tag 确定。没有并行维护需求时，不额外创建永久 `develop` 或维护分支。
- 新分支遵守仓库及运行环境的前缀要求。环境要求 `codex/` 时可使用 `codex/feat-主题`、`codex/fix-主题`、`codex/docs-主题`；不为统一名称擅自重命名已有分支。新任务按实际基线分支创建；紧急修复从对应正式 Tag 或已核实维护分支起步，避免夹带主干未发布功能，修复后回灌主干。
- 推送前审阅目标分支到拟推分支的全部提交与 diff，明确分支、Tag、Release 哪些属于本次授权。当前分支含其他未发布工作时，为仅同步规范等独立任务建立隔离分支，不顺带推送这些提交。
- 普通功能优先经 PR 和必要检查集成；没有 CI 或独立审查时如实记录已有的本地验证。合并、变基或冲突解决可能改变源码提交；发布包必须来自最终选定的发布提交，不能沿用其他提交的包。

## 判断版本

优先遵守用户指定版本及仓库明文规则。本技能默认使用两段“大版本.小版本”，沿用已有 v 前缀；用户指定精确标签字符串时原样使用。不要因为本地开发号更高就机械延续开发号。

| 实际影响 | 选择 | 示例 |
| --- | --- | --- |
| 兼容的功能新增、体验改善、修复 | 小版本加一 | 1.0 → 1.1 |
| 破坏配置/数据/API 兼容，或核心使用流程、产品能力发生实质重构 | 大版本加一，小版本归零 | 1.3 → 2.0 |
| 仅文档、格式、测试或内部重构，无用户行为变化 | 通常仅提交，随下一次功能发布 | 不单独打标签 |

若仓库明确使用三段 SemVer，则兼容修复升 PATCH、兼容新增升 MINOR、破坏兼容升 MAJOR。说明选择依据，不能把本技能的两段规则伪称为 SemVer。实现迁移可以消除兼容破坏时先评估该路径；依据最终行为判断。多类改动取最高影响等级；混合提交不掩盖破坏性变化。

## 写明更新并验证

提交标题采用 `feat/fix/docs/refactor/chore(可选范围): 具体中文摘要`，避免“更新代码”“优化一下”。正文写出实际改动及原因、影响和验证；破坏兼容时加 `!` 和 `BREAKING CHANGE:`。示例：

```text
fix(repeat): 保留切换动作前配置的按键间隔

更新：S 与 Y+S 分别读取已保存间隔，切换后不再覆盖用户设置。
影响：兼容旧配置；修复已有行为，建议纳入下一小版本。
验证：填写本次实际执行的命令及结果；未执行时如实说明。
```

执行与改动相关的必要检查，检查最终 staged diff；失败时先修复或报告阻塞，不能宣称通过。使用真实多行消息文件配合 `git commit -F` 或 `gh ... --body-file/--notes-file`，避免 shell 转义破坏正文。

涉及功能且有对应文档时，询问是否同步，并给出更新大纲；用户已授权同步则直接执行。询问时涵盖发布所需版本/下载链接维护与功能文档说明，可建议分别处理。需要答案时可继续不依赖文档决策的工作，不能把沉默视为批准。用户拒绝文档更新时尊重选择，最终明确尚未同步的差异。

## 本地发行打包

1. 打包前按上述累计变更判断大小版本并确定本次版本，不能先用旧版本打包、等上传 GitHub 时再改号。正式标签的版本编号是基线；历史附件内部构建号不同，仅作为历史映射记录，不能据此退回旧编号序列。
2. 沿版本声明到构建入口的调用链检查：项目元数据、程序内版本/关于窗口、构建脚本取值、可执行文件版本资源（如有）、发行包文件名、包内使用说明及校验清单中的版本须一致；遵循项目规范记录 1.1 与 1.1.0 等规范化映射。优先让构建过程读取统一版本来源，避免各处硬编码漂移。
3. 将本次拟发布功能和版本变更纳入同一确定的已提交源码状态，从该提交的干净检出或隔离目录构建。打包授权不扩大提交范围；存在无关修改时隔离处理，不能把整份脏工作区作为发行源码。记录版本、完整提交 SHA、产物文件名及 SHA256、实际验证结果和相对上一正式版的更新清单，随产物保留。
4. 检查实际生成产物的内部版本、包内说明、文件名和清单，运行项目已有安装自检或必要的启动验证；源文件版本正确不代表包内正确。核对没有混入旧构建产物、凭据或本地用户数据。未通过时修复并重建，不能标记为可发布。
5. 同一仅在本地流转、尚未对外发布候选版本的重复构建不机械递增版本。已对外发布的 beta/rc 有新内容时递增候选序号；已发布正式版有新内容时按变更类型生成新版本。仅复现原已发布提交的构建时保留版本，但不能覆盖已发布附件。
6. 后续发布优先使用本次已验证的同一份产物，核对提交 SHA、版本与 SHA256；标签指向其构建提交。打包后源码或版本发生变化，必须重新构建验证；新增破坏性变化时重新判断大小版本，不能直接改压缩包文件名冒充更新。

交付本地包时同时给出：版本及大小版本依据、本次具体更新、构建提交、产物路径与 SHA256、已执行验证和待验收项。用户明确只要临时调试包时标明调试用途，发布前重新执行本节流程，不将其直接当成发行包。

## 发布与标签调整

- 正常发布：使版本声明、必要锁文件、更新记录、README、发布说明、标签与发行包内版本一致。可将 1.0 规范化为包元数据的 1.0.0，但须遵循项目规范并说明。发布说明基于两次发布间的实际 diff，写“新增/修复/兼容影响/验证与待验收项”，只列适用项，不复用上一版的测试数字充作本次验证。
- 发行包从拟发布提交的干净检出或隔离目录构建并记录提交 SHA；版本变更须先提交。不能直接打包含有无关未提交修改的工作区，否则标签源码与二进制可能不一致。
- 标签必须指向拟发布的已提交且验证过的提交；普通新版本创建新标签，不移动已发布标签。未授权推送/发布时，交付本地提交及版本建议即可，不创建远程 Release。
- 发行使用附注标签，已有可用签名配置时可使用签名标签；没有签名配置就说明未签名，不擅自创建签名凭据。标签附注记录版本、提交及关键验证，产物摘要保存在校验清单。只推送本次指定分支和标签，避免 `--all`、`--tags` 或强推误带其他引用。
- 发布前核对版本解析器、更新源和通道策略。测试版必须标记 GitHub prerelease，正式版才可成为稳定更新来源；仅识别数字版本或只查询 `releases/latest` 的客户端不自动支持 beta/rc。不能通过取消 prerelease 标记绕过限制。Tag 只定位源码；供普通用户下载的程序包还须作为 Release 附件上传，GitHub 自动生成的源码压缩包不能代替安装包。
- 用户明确要求已有 TAG 改名时：核实原标签解引用后的 commit、Release ID、附件名称/ID/摘要，保存恢复信息；新标签指向同一 commit。更新原 Release 的标签、标题、说明和相关下载链接，保留附件。只有核验新标签及原 Release 附件完整后，才删除此次被替换的旧标签；本地旧标签如指向不同对象则先处理冲突。目标同名标签指向其他提交、Release 不可变或权限不足时，停止相关写入并报告，不强推覆盖。
- 仅改标签不等于重新构建：附件内部若仍是旧构建号，在 Release 与下载文档明确说明编号映射，保留真实文件名及校验值，不把改名描述为新功能，也不将旧二进制伪装成重编译产物。如用户要求完整新版安装包，则从对应源码统一版本后重新构建验证，不能靠改文件名完成。
- 优先使用可满足操作的连接器；不足时用 git/gh/API。API 修改 README 等文件时先核实目标分支和最新 blob SHA，遇并发冲突重新检查，不能覆盖未发布的本地工作或顺手推送其他提交。重试前先读远程当前状态，避免重复发布。
- 完成后重新读取远程标签的 commit、Release 及附件；核对文档下载地址，并核验本地 diff 没有混入无关变化。报告 commit/版本/选择依据、更新清单、验证结果和实际链接；部分步骤失败就明确未完成部分。
